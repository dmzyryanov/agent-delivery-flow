# Decisions

The lasting decisions of the delivery flow, each with its reason and its
consequences. D1 to D21 were taken while the flow was built and run for the
project it was extracted from, and are stated here in that project's
neutral terms; D22 to D26 are the kit's own, made when it moved to GitHub.
Where a decision was amended, the entry states the rule as it now stands. A
project made from the kit records its own decisions after these, in this
file, numbered on from the last one here:
`node .claude/scripts/delivery-queue.mjs reserve` hands out the next id.

## D1 — Task intake lives in GitHub Issues; an issue is a candidate, not approved scope

**Decision:** Ideas, defects and chores are filed as GitHub issues on `project.repo`, not as a Markdown backlog in the repository. They are filed with `/create-task`, which checks for a duplicate first and writes the description from the templates in `.github/ISSUE_TEMPLATE/` (bug, idea, epic). Every issue opens with `## Problem`, four labelled lines: what is wrong, where it came from, what changes if we do it, what it costs if we don't.

**Labels** (D22). `type:bug`, `type:idea`, `type:chore`, `type:epic` say what the issue is; `area:frontend`, `area:backend`, `area:infra`, `area:docs` say where the work lands; `prio:1`, `prio:2`, `prio:3` is set by the owner at triage and by nobody else, and an untriaged issue carries none. The state labels: `state:ready`, set only on the owner's explicit word, except the narrow class the scheduled grooming makes ready (D14); `state:deferred`, the owner's too (D13); `state:grooming`, set by whoever is grooming the issue now (D13, D14); `state:needs-owner`, set by the scheduled grooming (D14). An issue carries at most one `state:` and one `prio:` label: whoever sets one removes the others in the same command.

**An issue is a candidate, not approved scope.** Filing, labelling or prioritising approves nothing, and agreeing an approach in chat is not an order to start delivery. The owner's `state:ready` is the request (D5). The agreed goal, criteria and design reference are recorded in the pull request that implements the issue, and the issue closes once the change is delivered.

**Why.** A Markdown backlog mixes product ideas and real defects with no way to tell them apart, sort them or say which matters. Issues sit next to pull requests, carry labels and priority, and close on delivery.

**Consequence: the why of a task lives partly outside Git.** Two things bound it. The pull request description is the requirements record for the task it implements, so the goal and criteria of anything built are in the pull request that builds it; and lasting decisions enter this log, in Git, rather than resting in issue comments.

## D2 — A role's limit is a mechanism the harness enforces, not a sentence in its definition

**Decision:** The sub-agent team is `developer`, `tester` and `reviewer`, with `tester-look` and `tester-process` as narrower variants of `tester` (D21) and `architect` as a read-only tool invoked on demand for one technical question. There is no coordinator sub-agent: the main session is the Coordinator. Each role's limit rests on something checkable:

- `developer` is the only definition holding `Edit` and `Write`.
- `tester` and `tester-process` keep `Bash` — they have to run the project's commands — and the main session fingerprints their worktree with `.claude/scripts/tree-fingerprint.sh` before and after the run and compares the readings itself, outside the tester's session; a reading the tester reports about itself is corroboration, not the check. A changed fingerprint discards that run's verdict: the worktree is removed, recreated at the reviewed SHA, and the verification runs again.
- `reviewer` holds no `Bash`, no `Edit` and no `Write`. It reads the output of `.claude/scripts/review-artifact.sh`, whose header records the base named in its brief, the reviewed HEAD and the tree fingerprint, plus the tree through Read, Grep and Glob. The script refuses to run in a tree whose HEAD is not the reviewed head, so the fingerprint in the header cannot belong to another checkout — the reviewer has no shell with which to notice if it did.

**Why.** `tools:` filters tool names, and the permission rules in `.claude/settings.json` are project-wide and cannot tell which agent is calling, so per-role filtering of Bash arguments is not expressible: a narrow allowlist would be prose again. The reviewer's claim could be made true by taking the shell away, so it was; the tester's cannot, so it gets the fingerprint, which detects a write rather than preventing one. The asymmetry is deliberate.

**Worktrees.** Each role works in its own worktree (D3), so verification runs beside implementation; each runs its own install, and `node_modules` is never symlinked between them: `node_modules/` in `.gitignore` matches a directory and not a symlink of that name, so a symlinked tree shows as untracked, moves the fingerprint and can be committed by accident. The Bash guard refuses such a commit (D9).

**The browser.** `tester` and `tester-process` hold the client-provided browser tools for the two judgements a spec cannot make, a rendered page against the design and changed behaviour on the deployed service; they confirm them with `ToolSearch` when needed and report NOT VERIFIED when absent (D4). Anything that must stay true later is a test in the same pull request. `reviewer` gets no browser.

**The reviewer's independence rests on a different model and on what its brief leaves out.** The reviewer runs on another model than the developer (D8), which a test checks by shape. Its brief is the fixed template of `docs/DELIVERY.md` step 4: the issue description verbatim — with a design link or acceptance criterion added in a comment, and nothing else from the comments — the artifact path, the base and the head, and for a reviewer started fresh in a correction round the previous reviewer findings verbatim; never Developer's or Tester's conclusions, nor a summary of the change or the fix. `reviewer.md` tells it to judge without such a part when it finds one and to say in its verdict that it was there. It works in a fixed order — failure paths and ordering, races included; sender-controlled input; whether each new test fails when the code is broken; whether the change could be smaller; documentation last — and grades a document that states current behaviour or a contract wrongly BLOCKER/MAJOR, changelog headings and historical wording MINOR. It is never resumed in a correction round (D10).

**The main branch** changes only through a merged pull request: the repository ruleset `/flow-init` creates where the plan allows, and the Bash guard's push rule everywhere (D26).

## D3 — Worktrees live outside the repository and are never auto-pruned

**Decision:** A delivery worktree is created outside the repository; the preflight, `.claude/scripts/delivery-preflight.sh`, prints a sibling path, `<repo>-worktrees/<task-branch>`. The preflight runs no `git worktree prune`. It lists the worktrees, names the entries whose directory is gone, the worktrees the run did not create — another task's in the queue or an attended session's, which `delivery-queue.mjs status` tells apart, to be left alone — and any worktree inside the repository, and leaves every removal to a person. `.gitignore` keeps `.claude/worktrees/`.

**Why a worktree is never inside the repository.** A path inside a checkout every session shares, and ignored so that it does not move the fingerprint, is exactly what `git clean -xdf` removes: one session tidying its own checkout deletes every other session's working tree. A worktree found there is named with that warning; the exit status is unchanged, since the tree is usually someone's live work and refusing to run is not how it gets moved.

**Why nothing prunes.** `git worktree prune` removes the entries of worktrees whose directory is gone, and after such a deletion those entries are the only trace that the trees ever existed. A stale entry of a crashed run and an entry whose tree another session was using until something deleted it are indistinguishable once pruned. Pruning is a deliberate act after reading the list, and the preflight prints the command.

**Why it names rather than fails.** The script cannot tell a live sibling session from the leftover directory of a finished run; failing on the second would block every later run until someone tidied up, which is the pressure that produces destructive cleanups. Naming costs one read and leaves the judgement with the person who can make it.

**The ignore entry stays** as damage control: without it, a worktree someone still puts inside the repository would appear untracked and move the tester's fingerprint (D2), turning a location mistake into a discarded verdict.

**A worktree is no lock** (D16). Tasks run side by side in worktrees of their own, and the delivery queue holds the lock. A fire never removes, prunes or cleans a worktree the queue does not know; a task's worktrees are removed when the task leaves the queue.

## D4 — A run's own agent-definition change does not reach its sub-agents, and tool access is checked, not assumed

**Decision:** Two facts about the runtime, each written as what was seen and what is inferred from it.

**A run's own change to `.claude/agents/` did not reach the sub-agents it described.** A sub-agent given a task worktree read its definition from the main checkout; and a `tester` verifying a branch whose copy of `tester.md` had removed the browser tools still held them. Inferred, not established: the definition in force comes from the main checkout (or from the directory the parent session was started in, which was the same path), or client-provided tools reach a sub-agent independently of the `tools:` line. The rule holds under every explanation: **do not expect a run's own edits to `.claude/agents/` to affect that run's sub-agents.** A definition change is verified after it is merged and the main checkout has it, by a fresh invocation in a session started after that — the next fire, or a new attended session — not by the run that wrote it. If the first explanation is the true one, the main checkout's branch state is part of every run's environment, a further reason the checkout stays on the main branch.

**Whether a sub-agent receives a client-provided tool is not reliable.** The browser tools were seen absent from a `tester` — `ToolSearch` found none of them — while the definition in the main checkout listed them, and present in another `tester` with a real call answered. A resumed agent re-reporting its tools is not a second observation, since a session's tool set is likely fixed when it starts; a second data point needs a fresh invocation. No rule about propagation is claimed in either direction. What follows is operational: a role that needs such a tool confirms it with `ToolSearch` from inside that role at the point of need, and when it is missing reports the criterion NOT VERIFIED instead of describing a page it did not see. Removing a role's grant on the strength of one such observation is what generalising from one costs. The detail is in `docs/tooling/claude-mcp.md`.

## D5 — Ready issues are delivered by unattended scheduled runs

**Decision:** A scheduled fire opens a session that delivers issues labelled `state:ready` in mode `full`, with no one present to ask, following `.claude/scheduled/delivery-cycle.md`. The procedure lives in the repository and changes through pull requests; the scheduler's prompt only runs the check and points at it (`docs/tooling/scheduled-fires.md`). Fires come on `schedule.cycle`, every 30 minutes around the clock by default (D16), from the desktop app's scheduled task or, optionally, a launchd job (D17).

**Why a local scheduler and not a cloud routine.** A delivery needs the private repository's checkout, `gh` authenticated on the operator's machine, the project's local resources (its test databases, Docker), the Figma MCP server and a browser. A cloud routine reaches none of them, and a delivery it could perform would be one that verifies nothing. Session-bound `cron` dies with the session that created it and is capped at seven days, so it would lapse silently.

**`state:ready` is the request.** The owner sets the label (or the scheduled grooming on its narrow class, D14); nothing else is waited for, and the run asks for no further approval — `docs/DELIVERY.md` mode `full` is the standing authority it delivers under. Candidates are the open issues carrying it and not `delivery:attended` (D18); they go by `prio:1`, `prio:2`, `prio:3`, then none — an unset priority means the owner has not ranked it — then by the fewest areas shared with the tasks in flight (D16), then the smaller number. An issue carrying two `state:` or two `prio:` labels is a fault the run reports (D22).

**The gates.** The owner-steps gate (D7); the double-take gate, an issue an earlier delivery run already claimed or finished (D18); the dependency gate (D16); the design gate: an issue labelled `area:frontend` with no design reference — a Figma link with a `node-id` when `design.figma` is on, otherwise a saved image or a description in the issue — is not implemented, since a run inventing a design produces the change nobody asked for; the run comments what is missing and removes `state:ready`. The idea template's `Design needed: no` waives it. An issue with no derivable observable acceptance criteria is passed over the same way.

**The label comes off when the task leaves the queue** — DELIVERED, BLOCKED, RECOVERED or STOPPED — the comment written first; a delivered issue is closed by hand after the verification, not by a closing keyword. A failure left in the label would be retried by every later fire against the same wall.

**Unattended means a question is an outcome.** Everything `docs/DELIVERY.md` says to ask the owner becomes BLOCKED, recorded on the issue, the pull request left draft and unmerged. A permission prompt has no such fallback: it stalls the session for hours. So `.claude/settings.json` sets no `permissions.defaultMode` — a project value can only be a prompting mode, and it outranks the user-level file — and Auto comes from the user-level `~/.claude/settings.json`, which the owner sets by hand; a scheduled session with no `defaultMode` anywhere starts in Manual. Every command the run and its sub-agents need is allow-listed; read-only built-ins need no rule. An ask rule is not lifted by a broader allow rule, so the procedure names every asked command as out of bounds and a step that would need one ends BLOCKED. The procedure lists the rules it relies on in a block, and a change that introduces a command adds its rule in the same pull request.

**The run stops what it started; ownership, not ports.** A process the run or a sub-agent starts is stopped by the PID recorded at its start (`$!`, or the PID the tool reports) before the step that started it reports: `kill <pid>`, then `kill -9 <pid>` about ten seconds later; a PID that will not die is reported. The port is confirmed quiet with `curl` on both sides of the kill, at the address the server binds; a wrapper that did not pass the signal on has its children found in the run's own process tree with `ps -o pid,ppid,command -ax` and killed by PID. Freeing a port by pattern, stopping a process the run did not start and `lsof` stay forbidden, a BLOCKED outcome: a sweep by port once killed a browser-pane helper. `kill` is deliberately not granted: an allow rule takes a command away from the mode's classifier, so `Bash(kill *)` would auto-approve `kill -9` against any PID, and a PID cannot be written into a narrower rule; each attempt goes to the classifier, which in Auto decides without a prompt. Granted instead: `ps -o pid,ppid,command` with `-ax` or `-p <pid>` only (wider forms print a process's environment), and `curl -sS http://localhost:*`. A command held only by a task id is stopped with `TaskStop` (D6).

**The suites' flags live in the project's commands**, `commands.test` and its kin in `.claude/flow.json`, not in what an agent types: agents and CI then run one command. A flag that forces the test runner to exit once its tests are done can cut a file's results off with exit 0 under load, so a suite's count one short of the base's is a finding, not a pass; a time limit per test fails a test that hangs instead of letting it hang the run.

**What is unchanged.** Every limit of `docs/DELIVERY.md`: the bounded correction rounds (D15), one delivery to the environment at a time under the lock (D16), recovery and tagging. A criterion that needs a rendered page nobody could see is NOT VERIFIED, and the run does not merge.

## D6 — A command that does not end on its own is never started in the foreground, and a task held only by its task id is stopped by that id

**Decision:** The rule is stated in `developer.md`, `tester.md`, `tester-process.md` and the cycle's procedure, and the main session's part in `docs/DELIVERY.md`.

1. **The gap.** A foreground Bash call that reaches its time limit is moved to the background by the tool, which reports a task id and an output file and no process id (`… was moved to the background (ID: <id>)`). Nothing recorded a PID for it, so stopping by PID (D5) gave the agent nothing to stop it by, and a test run left that way once ran for seven hours.
2. **Never in the foreground.** A command that does not end on its own by design — a dev server, a watcher, a preview — is never started in a foreground call, by the main session or a sub-agent: there it always reaches the limit and takes that path. It is started with `&` and its `$!` recorded, and stopped by that PID.
3. **A task held only by its task id is stopped by that id.** A command that does end — a suite, a build — can still outrun its call, and a call made with `run_in_background` holds a task id from the start. The agent that made the call stops that task with `TaskStop` before it reports, unless the tool has reported that it ended; a `TaskStop` answering that the task is no longer running counts as stopped, and the report says which. `developer`, `tester` and `tester-process` list `TaskStop`, loaded with `ToolSearch` `select:TaskStop` when it arrives deferred. A sub-agent that cannot stop the task names the task id in its report, and the main session stops it when it reads that report — a dev server left running would hold its port through the next step. An unattended run also stops, before it ends, every such task id not yet stopped, and names each in its final message; one `TaskStop` could not stop is reported for the owner, like a PID that will not die.
4. **By the task id, not a PID looked up later.** A PID found afterwards comes from searching the process list for the command, which is stopping by pattern, and may find the wrapping shell rather than the process; the task id is the tool's own handle on the agent's own call.
5. **Not taken: a sweep at the end of a run.** Telling the run's own processes from everything else on the operator's Mac is unreliable, and a cleanup by port once hit a browser-pane helper.
6. **No rule.** `TaskStop` is a tool, not a Bash command; it asks no permission, and no settings change.
7. **Long commands** expected over about 4 minutes run with `run_in_background` from the start, their output checked no more often than about every 4 minutes (D20), and are stopped by item 3.

## D7 — Issues are groomed with `/groom`; one that needs the owner carries an owner-steps checklist or `delivery:attended`

**Decision:** `.claude/skills/groom/SKILL.md`, invoked as `/groom`, grooms issues with the owner one at a time until only `state:ready` is missing. It proposes the issue itself — first those the scheduled grooming left as `state:needs-owner` (D14) — and never starts a delivery.

**An issue that needs the owner: checklist or label.** The owner's own actions before delivery — a repository or cloud setting, a secret, a token, a mailbox, DNS, a command needing the owner's access — go into a `## Owner steps before delivery` checklist on the issue. While a box under it is unticked, in the description or a comment, the delivery cycle passes the issue over, with no comment and its label kept, and takes it once every box is ticked. An issue whose delivery needs a person present carries `delivery:attended`, which the cycle's candidate list leaves out (D18).

**Two rules are in the repository, not in private memory:** `state:ready` is set only on the owner's explicit word, with the one exception of the scheduled grooming's narrow class (D14); and agreeing an approach in chat is not an order to start delivery. The skill states both; `CLAUDE.md` and `docs/DELIVERY.md` state the first.

**Why.** A note in an issue's text that nothing reads lets an issue that needs the owner be taken unattended and fail mid-delivery for want of the owner's access. A checklist and a label are read by the procedure.

## D8 — Each role pins its model and its effort in its own definition, invoked without a `model` parameter

**Decision:** Every tracked definition under `.claude/agents/` carries one `model:` line naming a full model ID — `claude-` and a version, not an alias, not `inherit`, not a `-latest` ID, which moves like an alias — and one `effort:` line holding `low`, `medium`, `high`, `xhigh` or `max`. The pins today: `developer` `claude-opus-5-5` at `xhigh`; `tester` and `architect` `claude-opus-5-5` at `high`; `reviewer` `claude-sonnet-5-5` at `xhigh`; `tester-look` and `tester-process` `claude-sonnet-5-5` at `xhigh` (D21).

1. **Why.** An alias naming the main conversation's own family runs a sub-agent on the main conversation's exact model, and an omitted `effort` inherits the session's: each role's model and depth followed whatever the session was set to and changed without a pull request. A role's model is a reviewed line in the repository.
2. **No `model` parameter when a role is invoked.** A `model` given in the Agent call overrides the definition's, and the Agent tool accepts only aliases there, so a Coordinator passing one would undo the pinned ID. `docs/DELIVERY.md`, the procedures and the skills invoke every role without one.
3. **The reviewer is never on the developer's model** (D2): a reviewer on the developer's model is not an independent check. A test checks it by shape, never by value.
4. **Checks.** A test requires the two lines of every definition by shape, so moving a role to another model is an edit to its definition alone. Whether a pin takes effect is checked after the merge, in a session started after it (D4): the role, invoked without a `model` parameter, must show the pinned model in its transcript, and the result is noted on the pull request or the issue.
5. **A pinned full ID needs a recent enough Claude Code.** An older CLI refuses an ID it does not know before the role starts (`API Error: 400 … does not support this model`). A refused ID stops that role before it starts, so until the line is reverted every delivery of the cycle ends BLOCKED there: check a new pin with the Claude Code the scheduled sessions run.
6. **Cost and rollback.** A pinned ID misses a model upgrade until a pull request changes it, which is the point of pinning. A move to a cheaper model or effort follows D21's replay. Undo: revert the line.

## D9 — A hook run before every Bash call, `.claude/scripts/guard-bash.mjs`, refuses the few commands that must never run

**Decision:** `.claude/settings.json` holds `hooks.PreToolUse`, matcher `Bash`, one command hook, `node "${CLAUDE_PROJECT_DIR}/.claude/scripts/guard-bash.mjs"`, `timeout: 10`. The hook receives JSON with `cwd`, `tool_input` and, inside a sub-agent, `agent_id` and `agent_type`; exit 2 refuses the call with its one line on stderr, exit 0 leaves it to the permission rules. It adds no allow, ask or deny rule.

1. **Why.** Rules such as "never `lsof`, never a sweep by port", "never symlink `node_modules`" and "never commit or push to main" existed only as prose, which works while an agent remembers it; a sub-agent does not load the main session's memory, and a sweep by port once killed a browser-pane helper. A hook runs before the call, in the main session and inside sub-agents, and can refuse it.
2. **What is refused.** In every session: `git commit` where the target directory's branch is `main`; `git commit` where a `node_modules` of the target worktree is a symlink; `lsof` fed into `kill` — in its pipeline, in a substitution among its words, or through a variable or a file it was written to, followed by name across the line through at most eight hand-overs; `pkill`; `killall`; every merge that does not go through the delivery queue (D16, D22); a push to the main branch and any force push (D26). Inside `developer`, `tester` and `tester-process`, told by `agent_type`: any `lsof`. Inside any sub-agent, told by `agent_id`, which only a sub-agent's hook input carries: the outside review and Codex (D12).
3. **The commit rules hold in this repository only** — the one `CLAUDE_PROJECT_DIR` names, recognised by the git directory all its worktrees share — because sub-agents build throwaway repositories with `git init -b main` to test the scripts, and the rule being enforced is about this repository's main. The target directory is the one a preceding `cd`, `pushd` or `git -C` names, else the input's `cwd`; where the guard cannot know it (a variable, a substitution, `cd -`), the commit passes rather than fall back on `cwd`, because the session's `cwd` is the main checkout on `main` while every commit is made as `cd <worktree> && git commit …`.
4. **How a command is read.** Split into segments on `;`, `&&`, `||`, `|`, `&`, line breaks, substitutions and subshells, quotes respected; each segment judged by its leading words, never by a substring, so a commit message, a `grep` pattern or a here-document that names `pkill` passes. Assignments, shell keywords and the commands that run the one named after them (`sudo`, `env`, `command`, `exec`, `nohup`, `time`, `nice`, `timeout`, `caffeinate`, `xargs` and the rest) are passed over; `$'…'` is decoded as bash and zsh decode it; names are matched in any letter case, since macOS runs `PKILL`; a glob no quote protects in a command's name stands for every refused name it could match.
5. **It fails open**, except where a rule says otherwise: input that is not JSON, a command it cannot read to its end, and an error of its own pass with exit 0, and so do a missing `node`, a crash and a timeout. It stops waiting for stdin after 3 s and gives a `git` call at most 1.5 s, ending inside the hook's 10 s. Two rules fail closed: the merge rule, for a command it cannot read that names `gh` (D16), and inside a sub-agent the outside-review rule, for one that names `outside-review` or `codex` (D12). A guard that refuses wrongly stalls an unattended run; one that lets a command through leaves the rule where it was, in prose.
6. **A habit breaker, not a security boundary.** It does not look into `sh -c`, `eval`, a variable or an alias holding a command name, a function, a script file, a brace expansion that builds a name, a renamed copy or a link, `npx`, or another HTTP client; there the rules stay prose. It grants nothing: whatever it lets through goes to the permission rules and the mode's classifier unchanged.
7. **The refusal** is one line on stderr: `guard-bash refused this command:`, the rule, the allowed alternative — commit on a task branch; run the install in the worktree instead of linking `node_modules`; stop by the recorded PID or with `TaskStop`; merge through the queue — and `[PreToolUse hook .claude/scripts/guard-bash.mjs, <decision>]`, the decision that carries the rule — D9, or D16 for a merge, D12 for the outside review, D26 for a push. It never repeats the command, so it is not taken for a permission prompt; nothing waits for an answer.
8. **Checks and rollback.** The tests run the guard as the hook does, against throwaway repositories, each refused form beside what must pass, and hostile shapes at growing sizes. That the hook is loaded is confirmed with a harmless refused form, `pkill -0` on a name no process carries, not assumed. A wrong refusal in an unattended run ends it BLOCKED with the guard's line quoted. Undo: revert the merge commit that brought the hook, which removes the `hooks` key and the test that requires it.

## D10 — A correction round: APPROVED WITH MINORS may merge, a Markdown fix to named minors carries the verdicts forward, Developer and Tester are resumed only within 5 minutes and Reviewer never, and each report opens with a fixed first line

**Decision:**

1. **Merge with minors.** Reviewer APPROVED WITH MINORS and Tester PASS may merge the reviewed SHA; minors left unfixed are recorded in the pull request or in a follow-up issue.
2. **Carry-forward, with its safeguard.** If minors are fixed, the Reviewer verdict and the Tester PASS carry forward to the fix commit only when all four hold: `git diff --name-only <reviewed SHA> <fix SHA>` lists only `*.md` files; none of them is `CLAUDE.md`, `docs/DELIVERY.md`, `CHANGELOG.md`, a file under `.claude/`, a contract document of a part `docs/ARCHITECTURE.md` lists under `Stable parts`, or a Markdown file the product serves or ships at run time — the documents that direct the delivery, state a contract or are published; every changed hunk is at a place one of the reviewer's numbered minors named, checked hunk by hunk; and the fix commits sit directly on the reviewed SHA, with no integration of main between. The Coordinator records in the pull request the reviewed SHA, the fix SHA, the files and the finding number each hunk answers. A comment-only change in a code file does not carry forward. CI must still pass for the merged SHA: a verdict carries forward, a check run does not. A fix outside the carry-forward is re-checked as D19 says; a fix answering the outside review never carries a verdict forward (D12).
3. **Resume or start fresh.** Developer and Tester are resumed only if their last report arrived under 5 minutes ago, while their prompt cache still holds; otherwise a fresh one is started with the branch, the base and head SHAs, the numbered findings and its previous report. Reviewer is never resumed in a correction round: it always starts fresh, with the brief of `docs/DELIVERY.md` step 4 and the previous reviewer findings verbatim, so it judges a fix without its own earlier verdict in view.
4. **A fixed first line**, with no word cap on the rest, each a fenced line of its definition: `Verdict: <APPROVED | APPROVED WITH MINORS | CHANGES REQUESTED> · base <sha> · head <sha> · <n> findings` (reviewer); `Verdict: <PASS | FAIL> · base <sha> · head <sha> · <p> PASS, <f> FAIL, <n> NOT VERIFIED` (tester); `Final <sha> · checks: <the checks run> · unfinished: <n>` (developer), and `Handover <sha> · …` for a handover (D20). Reviewer findings are numbered, which the carry-forward and a fresh role's brief rely on.
5. **Why.** Re-reviews after APPROVED WITH MINORS almost never found anything blocking; a sub-agent's prompt cache lives 5 minutes while rounds arrived after 7–9, so most resumes rewrote the whole context; and the verdict was often buried deep in a report.
6. **Risk.** A documentation fix can add a wrong statement nobody independent reads; the safeguard limits it to hunks the reviewer named, in documents outside the excluded list. Undo: revert.

## D11 — Several tasks given at once are implemented in parallel; a scoping chat ends in a written issue; every `gh` command names the repository and a merge the checked SHA

**Decision:**

1. **Several tasks at once.** Tasks the owner gives at once are implemented in parallel without asking again, each on its own branch in its own worktree, each registered in the delivery queue and merged one at a time under its lock (D16). Each integration of main into a branch is a merge commit, not a rebase; after it, the review artifact of a whole-change review is taken against the main SHA merged in, so it shows the branch's whole change, conflict resolutions included, and nothing of the branches merged before it.
2. **An agent stopped by a session limit.** A Developer or Tester stopped by a session limit — which is not a report, so D10's 5-minute rule does not apply — is resumed with `SendMessage`, after the main session has inspected its worktree (uncommitted diff, debug lines, containers still up) and told it what it found. A Reviewer so stopped is started fresh with the brief of `docs/DELIVERY.md` step 4.
3. **A scoping or grooming chat ends in a written issue**, not a delivery; grooming follows `/groom`.
4. **Merge control in the process document.** `docs/DELIVERY.md` states that every `gh` operation names `--repo <project.repo>`, that a merge names the checked head SHA (`--match-head-commit`, run by the queue, D22), and that no direct push to the main branch or force push is authorised.
5. **Hygiene, in `CLAUDE.md` once**, since sub-agents load `CLAUDE.md` and not the main session's memory: each agent writes in the shared scratchpad under a file-name prefix of its own, and its decisive evidence is what it printed to its own stdout; an agent that runs suites binding ports or using a database takes ports and a database of its own (`commands.taskTest`, D16) and removes what it started; commit messages are written with `git commit -F <file>`, because a `commit && commit` heredoc chain once lost both subjects.
6. **Who draws the design.** Where `design.figma` is on, Claude draws two or three directions for a new screen in Figma, which the owner approves before implementation; a role does not edit the canvas.
7. **Why.** Rules kept in private memory notes reach sub-agents only through briefs, which carried them unreliably; nobody reviews them, and a new machine does not have them.

## D12 — Outside review by Codex: the main session runs `.claude/scripts/outside-review.sh` once on the approved SHA, only where the project enabled it and for the areas it named, with a quarter of the allowance kept for the owner, and a skip never stops a delivery

**Decision:**

1. **When it runs.** Only when `outsideReview.enabled` in `.claude/flow.json` is true; otherwise the script skips and the pull request records why. Then at most once per task, on the final candidate after Tester PASS and Reviewer APPROVED, or a verdict `docs/DELIVERY.md` step 5 accepts in their place after the third round (D15), and only when the branch touches an area `outsideReview.areas` lists; never for documentation or process text alone, and never a second time on the fixes it caused. The main session runs it; no sub-agent does (D9).
2. **Its findings.** The Coordinator posts Codex's notes on the pull request verbatim, in one comment naming the reviewed SHA and the model, and answers every numbered finding there: fixed in `<sha>`, declined with the reason when it is wrong, or a follow-up issue. Blocking findings inside the task's scope are fixed within the round cap, after the third round only a blocking defect (D15). Declining a blocking finding about a material risk is asked of the owner in an attended session and ends an unattended run BLOCKED with the draft pull request and the finding named. Fixes answering it never carry a verdict forward (D10) and are re-checked as D19 item 4 says.
3. **The script** pins the model, `gpt-6-astra` at `xhigh`, and a fallback, `gpt-6.1-sol`, run once and only when the first was refused for its allowance; runs `codex exec` read-only, ephemeral, with Codex's core shell environment only, the issue and the artifact between per-run tokens; requires a login with ChatGPT and takes the API-key variables out of Codex's environment; refuses wrong input (exit 2); and answers a skip with exactly one line (exit 3), never a verdict. Login evidence wins over allowance evidence, so an expired login asks the owner to sign in rather than buy credits. Changing a pin is a pull request. The detail is `docs/tooling/codex.md`.
4. **The owner's quarter.** No run while the 5-hour or the weekly window is over 75% used, unless Codex credits can be spent; a window at 100% with none is the allowance used up, a skip for the owner.
5. **A skip never stops a delivery.** The pull request records it and merges on the internal verdicts. A skip only the owner can clear — Codex missing, not signed in or not with ChatGPT, the login expired, the allowance used up — is reported once until it is fixed: the script records its key as pending; the caller tells the owner (in an attended session in the chat; in an unattended run in the result comment and one `PushNotification`) and then acknowledges that key alone with `--reported <key>`; a key left pending is reported again at its next occurrence. The record is `~/.local/state/agent-flow/<repo-name>/outside-review-reported.json`, outside the repository, holding nothing but the keys. A fault errs on telling the owner twice, never on not telling them.
6. **Permission.** One allow rule, `Bash(sh .claude/scripts/outside-review.sh *)`; `codex` and the helper are not allow-listed.
7. **Privacy.** The diff and the issue text go to OpenAI under the owner's ChatGPT account; the owner agrees to that by enabling it. Credentials are never in Git, Codex runs in a worktree without `.env`, and its brief tells it to read only the tree.
8. **Why.** Every internal review is by the developer's vendor; an outside model found races and defects after the internal reviewers had passed the change. It is a second reading, not a guarantee, and where a blocking automated test can cover a risk, the test is preferred.
9. **Rejected.** A manual relay by the owner (costs the owner time, cannot run unattended); an OpenAI API key (a new paid service and a credential to keep); driving the ChatGPT site through a browser (a page and a login an unattended session cannot rely on).

## D13 — A grooming chat marks the issue it holds `state:grooming`, and an issue the owner has put off carries `state:deferred`; the automatic pick passes over both and the delivery cycle ignores both

**Decision:**

1. **`state:grooming`: someone is grooming this issue now.** Set by `/groom` as soon as an issue is taken — the pick, or one the owner names — and by the scheduled grooming (D14); never by the owner or `/create-task`. Just before the take the skill re-reads the issue's labels: a pick that has gained `state:grooming`, `state:deferred` or `state:ready` since the list was fetched is replaced by the next one. An issue carrying `state:ready`, re-groomed on the owner's word, never gets it.
2. **`state:deferred`: the owner has put this issue off.** Set and removed only on the owner's explicit word, as `state:ready` and `prio:` are. Naming a deferred issue to groom is the owner's word that removes it; postponing a ready issue replaces `state:ready`.
3. **Release.** `state:grooming` comes off when grooming of the issue ends: the owner swaps the pick, says ready, sets it aside or postpones it; each case has its one `gh issue edit` command, which removes the other state labels it replaces (D22). A pick swapped because another chat holds it keeps the label.
4. **Who reads them.** `/groom`'s automatic pick passes over both, and its reminder line names the issues carrying `state:grooming`. The delivery cycle ignores both: its candidates are `state:ready` issues only.
5. **An abandoned chat** leaves `state:grooming` behind and nothing expires it; the reminder line and the chat titles show it, and the owner releases it by naming the issue in a grooming chat.
6. **Why.** Nothing marked an issue in progress, so a second grooming chat proposed the issue the first held; and a postponed issue kept coming up as the next pick.

## D14 — A scheduled task grooms one open issue every 15 minutes, strictly one run at a time: a narrow class of small bugs and chores invisible to users becomes `state:ready` without the owner, every other issue waits as `state:needs-owner` with its questions, design directions and delivery notes prepared

**Decision:** `.claude/scheduled/grooming.md`, fired on `schedule.grooming` (every 15 minutes, off the delivery cycle's minutes) by the same scheduler as the cycle (D17). It writes to issues and never to the repository: no worktree, no commit, the main checkout left as it was.

1. **Why.** An issue became deliverable only after a grooming chat with the owner, so the supply of ready issues was the owner's free time; and what grooming wrote decided correction rounds — a limit whose bypasses grooming did not name cost a round each.
2. **One run at a time, recognised from GitHub.** A run claims its issue with a comment, `Grooming run <fire time>: taken`, before it sets `state:grooming`. A fire that finds a claim under two hours old with no result after it ends at once; at two hours or more that run died, and the fire takes the issue over with a claim naming it. Every write is preceded by a re-read: only the run whose claim is the newest `Grooming run` line writes a description or a label, and a run whose claim is no longer newest posts its result as a comment and changes no label, so neither result overwrites the other.
3. **One issue per fire.** Candidates carry no `state:` label and are issues the owner has not seen — no grooming result, no release to a `/groom` chat, no `state:grooming` ever added (D17); returned by the delivery cycle first, then by `prio:`, then an issue another names in `Depends on #N`, then the smaller number. No grooming while 10 or more issues wait as `state:needs-owner` (D17).
4. **The tree.** Claims are checked against freshly fetched `origin/main`, exported into the session's scratchpad by `sh .claude/scripts/export-origin-main.sh <scratchpad>`, one allow rule; the script holds the checks — one absolute path to an existing directory under `/private/tmp/claude-`, no `origin-main` there yet, `refs/remotes/origin/main` by its full name. No rule grants `tar` or `git archive` themselves: a prefix rule would also auto-approve options that run any program.
5. **Two looks**, started together and invoked without a `model` parameter: `architect` on the approach, files, documents, version, size, risks and overlap, and `tester-look` (D21) on how each criterion is checked and the attack list. The run fingerprints the main checkout before and after them and compares the readings itself; a mismatch sends the issue to the owner.
6. **What the issue gets:** `/groom`'s steps against the export, a `## Touches` line of area names from `.claude/delivery-areas.json` — the files the architect names mapped with `delivery-queue.mjs areas --files`, an area added when in doubt, since a missing hard area lets two conflicting tasks run at once — and `## Delivery notes`, a starting point checked again at delivery. A visual change gets two or three directions in Figma where `design.figma` is on, desktop only, on a new page; a missing or refused Figma write tool sends the issue to the owner with what to draw.
7. **Two outcomes**, each a comment opening `Grooming run <fire time>:`. **Ready without the owner** only on the class the procedure gives word for word: a small `type:bug` or `type:chore` in one area, needing no new decision, invisible to users, outside the hard area `delivery-process` and `delivery:attended`, with no owner steps, no design, no claim or result of an earlier delivery run and no earlier `ready without the owner` comment; unclear means not. **Waits for the owner** (`state:needs-owner`) with `## Questions for the owner`, numbered, each with options and a recommendation. The owner undoes a ready by removing the label, and no run sets it on that issue again.
8. **No overwrite.** A checksum of the description taken at the take is compared just before writing; a description changed meanwhile is not replaced — the groomed text goes into the result comment and the issue waits for the owner.
9. **One morning notification.** The fire at `schedule.morningFire` (09:07 by default, a window one cadence long) sends one `PushNotification` in `project.ownerLanguage`: the issues made ready without the owner since the same hour the day before, and the count waiting for the owner. A morning the Mac slept through sends none.
10. **`/groom`** proposes the `state:needs-owner` issues first, presents what the run prepared rather than deriving it again, and re-checks against fresh `origin/main` before ready.
11. **Risk and rollback.** A fire that misjudges the class makes an issue ready that the cycle may deliver at its next fire; the class is narrow, unclear means not, and the delivery's own verification still applies. Undo: disable the scheduled task or job.

## D15 — At most three correction rounds: after the third only a blocking defect is fixed and every other finding becomes a follow-up issue

**Decision:**

1. **The cap.** A delivery has at most three correction rounds, and the cap asks no one for permission. Within it in-scope defects are fixed autonomously, and a reassessment with the relevant specialist after two attempts without progress still applies.
2. **What a round is.** A Developer fix and its re-verification by Reviewer, Tester or both. Not a round: a Markdown fix whose verdicts carry forward (D10); a wording fix the Coordinator makes itself (D19); merging main in, unless it needs a fix; the full pass a critical area gets on the SHA to merge (D19) — a fix it calls for is one. A wording-only fix to a file D10 excludes is a round.
3. **After the third round** only a blocking defect is fixed. Every other finding — Tester, Reviewer or Codex — becomes a follow-up issue filed by `/create-task`'s rules, and the pull request lists them. The Coordinator rates every finding still open in the latest verdicts as blocking or not; one rated not blocking is filed as a follow-up with one sentence on why, and a verdict whose every open finding is so filed no longer stops the merge: `docs/DELIVERY.md` step 5 accepts it in place of PASS or APPROVED, and CI must still pass for that SHA. A blocking defect still open is fixed, in an attended session, in further rounds limited to it, the owner told after each what is being fixed and why; an unattended run ends BLOCKED with the draft pull request and the defect named.
4. **Blocking**, defined once in `docs/DELIVERY.md`: in a realistic case data is lost or corrupted, one client can take the service down, data leaks, or a documented contract breaks — plus what the project's priorities in `CLAUDE.md` add. A hostile shape outside the issue's stated scope is a follow-up, not a blocker.
5. **Outside review** runs at most once per task, on the final candidate (D12).
6. **Reporting.** In an attended session, after the second round the Coordinator tells the owner, unasked, why the delivery continues and what is left.
7. **A follow-up filed unattended** follows `/create-task`'s rules with no one to ask: a duplicate among the open issues gets a comment instead; the issue is written from the template without `state:ready`; it is filed with `gh issue create --repo <project.repo> --title '<title>' --body-file <file> --label <labels>`, which carries no command substitution, the title in single quotes; the result comment lists the issues filed in place of the owner's retelling.
8. **Why.** Deliveries went round after round of fixing and full re-checking until no checker found anything new; most of their time went into correction rounds, and more rounds did not catch the defect that mattered most.
9. **Risk.** A non-blocking defect found after the third round reaches main and waits in a follow-up issue the owner can see and order; the blocking definition keeps lost data, a service taken down, a leak and a broken contract out of that path.

## D16 — The delivery cycle: a fire every 30 minutes around the clock takes the ready issue that overlaps the tasks in flight least, up to three tasks are developed side by side, and merge, deployment and smoke happen one at a time under a lock the queue script holds

**Decision:**

1. **Why.** Delivered one at a time and only in a nightly window, ready issues waited most of a day and fires stopped because another delivery's worktree existed. Parallel tasks with one serialised merge raise throughput, bounded by the plan's limits.
2. **The cycle** (`.claude/scheduled/delivery-cycle.md`), fired on `schedule.cycle`. Each fire, in order: its checks — the main checkout on the main branch, `gh auth status`, `git fetch origin` (retried once after 10 s on a git lock another fire holds), the project's local resources — a failed check ending the fire with nothing claimed; then the first task in the queue whose session is no longer alive, or detached, is adopted and continued from its saved step; otherwise one new issue while a slot is free; and every fire ends with the status table. A fire takes at most one new issue.
3. **The queue**, `.claude/scripts/delivery-queue.mjs`, one Node file whose header is its contract. Its state is one JSON file under `$(git rev-parse --git-common-dir)/delivery-queue/`, the same from every worktree and never in Git, mode 0600. Every change is made holding a mutex, read whole and written by a rename; a state not in the shape the script writes is a fault that changes nothing, never an empty queue, which would release the lock. The mutex is a file hard-linked into place; a stale one — its process gone, or older than 30 s — is taken over through a claim that exactly one process can make. Every command that acts on a task names its session, and a task belonging to another session is refused (`belongs to`); a session that lost its task stops acting on it.
4. **Slots.** At most 3 tasks are `working` (`set slots <n>`). Awaiting the lock, paused, or delivering under the lock holds no slot. A task coming back to work takes its slot back even over the limit; new starts wait.
5. **Areas and the pick.** `.claude/delivery-areas.json` is the vocabulary: hard areas — migrations, the API contract and shared types, dependencies, CI and deployment, the delivery process — and ordinary areas, each mapped to path globs; the bookkeeping files count in no area. An issue names its areas in `## Touches`; none means every area. A task in flight touches what it declared plus the areas of the files its branch changed. `pick` passes over, keeping the label: an issue whose task is still in the queue; one with an open `Depends on #N` (at most twenty looked up); one sharing a hard area with a task in flight; one touching every area while any task is in flight. The rest go to the gates by priority, then the fewest shared areas, then the smaller number; `start` re-reads the issue and refuses what `pick` would pass over, so two fires cannot both start conflicting tasks.
6. **Liveness.** The scheduler's run status is no sign of life: a run waiting between turns reads as finished. A session counts as alive while the newest of its transcript, its sub-agents' transcripts and its task's last queue update is within 90 minutes (`set stale-minutes`); the longest quiet wait in a delivery is a background review run. An attended session's task (`start --day`) is adopted only once its session detached it, however long it is quiet, since the owner may come back. The adopting session reads the actual state on GitHub — the pull request, main's run, the tag — and goes on without repeating what is done.
7. **The delivery lock**, one pull request at a time: integrate current main by a merge commit, set the version, re-check as `docs/DELIVERY.md` step 4 says (D19), merge, follow the main workflow (`delivery.mainWorkflow`) through deploy and `delivery.smokeJob`, check `project.site`, tag. With `delivery.deploy` false, that is the main workflow's run for the merge commit passing. The lock is released after that, or after a verified recovery. `lock` takes it with a new token; `--wait` (at most 25 minutes, run in the background) serves the longest waiter; the holder runs `check` before merging and tagging and after every wait. A fix needed after integration releases it with `unlock`. A failed recovery pauses the queue, and no task takes the lock until the owner's word.
8. **No bypass.** The one way to merge is `merge <task> --token <token> --sha <sha>`, which checks the token and that the queue is not paused, records the request, and runs `gh pr merge <n> --repo <project.repo> --merge --match-head-commit <sha>` itself (D22); the Bash guard refuses every other way (D9). An attended session merges the same way, so it registers its task with `start --day` first.
9. **Versions and decision ids.** `VERSION` and the changelog heading are set under the lock against main at that moment, so parallel branches never collide; decision ids are reserved from the queue's counter (`reserve`) when a task needs one, starting after the highest id on `origin/main`, so parallel branches never take the same id.
10. **State, recovery and the label.** A resumed task checks GitHub before acting: never a second pull request for a branch, never a merge of a merged one, never a tag that exists. The round cap counts per task (`update --round`). An unavailable resource — a plan limit, Docker, GitHub, Actions minutes — pauses the task, detached and holding no slot, and a later fire resumes it, putting it back to work. `state:ready` comes off when the task leaves the queue; a task's worktrees and test resources (`commands.taskDown`) are removed then.
11. **Isolated test resources.** Tasks' suites run at once, so each task's runs on its own database and ports through `commands.taskTest`; with it empty, `commands.test` runs, and the project's suites must then not share state they write.
12. **Reports.** `status` per task; from 09:00 to 22:59 a DELIVERED, BLOCKED or RECOVERED result and a paused queue reach the owner as one `PushNotification`; at other hours the result comment and the final message carry them.
13. **CI.** The main workflow's deploy job runs in one concurrency group that never cancels a run in progress, so an older run cannot overwrite a newer release; every integration of main runs the pull request's checks again, so more tasks in flight spend more Actions minutes.
14. **The scheduler, as measured.** A fire of a scheduled task is dropped, not queued, while a run of the same task is inside an active turn; a run that has ended its turn to wait on background work holds no fire back, and fires of different tasks run side by side. So one task every 30 minutes is enough for parallel work, and the procedure makes its long waits in the background so that its turn ends.
15. **Rejected.** One scheduled task per slot (one task's fires already run side by side); the scheduler's run status as liveness; a lock held by a server or daemon (the sessions, worktrees and transcripts are all on the Mac); merge order, versions and ids fixed up front (fires start tasks independently); building on unmerged branches (a dependent task waits for its predecessor's delivery).
16. **Risk and rollback.** Three tasks at once spend the plan's limits about three times as fast while they run. Undo: revert, then remove the state directory and the tasks' test resources by hand once no task is in flight.

## D17 — The scheduled fires check for work before a session reads its procedure; launchd behind a check that spends no tokens is the cheaper path; the grooming takes only issues the owner has not seen, and none while 10 or more wait for the owner

**Decision:**

1. **Why.** A fire that opens a full session pays its fixed context — tool schemas, `CLAUDE.md`, memory — and then the procedure's reading of `CLAUDE.md` and `docs/DELIVERY.md`, whatever it then finds; most fires find nothing to do, and an empty fire cost about $0.3–0.5.
2. **The check**, `.claude/scripts/fire-check.mjs <cycle|grooming>`, Node with no dependencies. It prints one line, `work: <reason>` or `skip: <reason>`, and only reads: no claim, comment, label or queue write. Its skips are only the procedures' own stop conditions; what it cannot tell — a command failing, hanging or answering garbage — is work, so a fault costs a session, never a fire that had work. With work, a precondition that fails (GitHub, the remote, Docker where the project needs it) is a skip naming it, since the session's own checks would end the fire at once. `delivery-queue.mjs status --json` and `pick --json` give it the queue without a text table.
3. **Two schedulers, one procedure.** The desktop app's scheduled tasks are the default, which `/flow-init` creates: their prompt runs the check first and stops on a `skip:` line, which saves the procedure's reading but not the session's fixed context. The launchd jobs are the optional, cheaper path: `.claude/scripts/scheduled-fire.sh <job>` runs the check and starts a session only with work, as the app-bundled headless `claude -p` with the procedure's pointer, an explicit `--model` and `--effort`, `--permission-mode auto`, under `caffeinate`, in a clean environment — the app's inherited variables broke the session's sign-in — with `PATH` set by the script. They need the owner's own `claude auth login`. Never both: every procedure would fire twice. `docs/tooling/scheduled-fires.md` holds the detail.
4. **The launchd locks.** One per job. The cycle's goes at the run's first `result` line: a headless run lives on until its background sub-agents finish, and a run waiting between turns must not stop the next fire (D16). The grooming's is held until the process ends, strictly one run at a time (D14). A supervisor process holds it, so the launchd job itself ends within seconds and launchd passes no fire over silently.
5. **Headless sessions.** No scratchpad is named in the system prompt: the session id is `$CLAUDE_CODE_SESSION_ID`, and the scratchpad is the path a desktop session would be given, under `/private/tmp/claude-<uid>/`. Transcripts are where every session's are, so the queue reads liveness the same way. Whether `PushNotification` reaches the owner from a headless run is not measured, so the grooming's morning run also shows its result as a macOS notification.
6. **The grooming throttle**, in the procedure itself so that a run started for another reason does not groom past it: no grooming while 10 or more open issues carry `state:needs-owner`, and candidates only issues the owner has not seen — no grooming result or release on them, no `state:grooming` ever added. An issue the owner has seen is theirs to settle in a `/groom` chat.
7. **Rejected.** The check in POSIX sh (it reads JSON); a cheaper model for empty fires (it still loads the same context); the check inside the session (the same); a daemon of our own (more to keep alive for the same calendar).
8. **Risk and rollback.** A check that wrongly says skip loses a fire's work until the next one that finds it. A paused task whose reason still holds makes every cycle fire start a session, the check unable to tell whether a plan limit has reset. Undo: `sh .claude/scripts/launchd/uninstall.sh`, and the desktop tasks again.

## D18 — Delivery asks one question, does it need a person present: only a yes, or a leftover branch of a scheduled run, keeps an issue out of the delivery cycle, labelled `delivery:attended` with an `Attended because:` line; the owner is called only when necessary

**Decision:**

1. **One question.** Grooming — `/groom` and the scheduled grooming alike — asks of every issue: does delivery need a person present? Only a yes keeps it out of the delivery cycle. Changing the delivery machinery — `.claude/`, the scheduled procedures, CI, `docs/DELIVERY.md` — is not by itself a reason.
2. **The owner is called only when necessary.** `docs/DELIVERY.md`, the skill and the scheduled grooming say it in the same words: "The owner has little time: a person is required only for an important change that cannot be delivered safely without them, never "just in case", for convenience, or because a change is large or touches the process. When in doubt, the answer is no." `CLAUDE.md` says it in one sentence.
3. **"Needs a person" is narrow:** the owner watches or checks something during or right after deployment; a step mid-delivery is one only the owner can run; or a decision is expected mid-way. An action the owner can take before delivery is a box of the `## Owner steps before delivery` checklist instead (D7).
4. **The leftover branch.** An issue a delivery run already took — its `Scheduled run <time>: taken` claim or a `DELIVERED`, `BLOCKED` or `RECOVERED` result stands — is never taken by the cycle again; its branch and pull request are finished in an attended session, and it carries the label with the reason `leftover branch from scheduled run <time>`.
5. **The label carries a reason.** Grooming sets `delivery:attended` only with a line of its own in the description, `Attended because: <reason>`: no reason, no label. The scheduled grooming, which has nobody to ask, answers no whenever the issue does not show the need. A label removed takes its line with it; removing it from a ready issue needs no further word from the owner, since it queues an issue the owner already approved.
6. **Attended, not by day.** The split is an attended session, the owner in the chat, against an unattended run — not day against night, since fires run around the clock. The queue's own names stay as the script has them: `start --day`, the origin `day`.
7. **No safeguard beyond the hard area.** A change to the delivery machinery delivered unattended counts in its hard area, `delivery-process`, or `ci-deploy` for CI, so two such changes never run at once (D16); a broken role or procedure shows as a BLOCKED result and a notification, and recovery is a revert. A change to `.claude/agents/` takes effect at the next fire (D4).

## D19 — A fix after the first verdicts is re-checked only by the role whose finding it answers, and only the fix; a branch in a critical area gets the full pair once more on the SHA that is to merge

**Decision:**

1. **Why.** After the first full verdict almost every fix went back to both roles, a one-sentence documentation fix included; about a third of all spend went into rounds after the first verdict, and documentation-only rounds were re-checked as fully as code.
2. **The rule** (`docs/DELIVERY.md` step 4, after D10's carry-forward). Anything outside the carry-forward is re-checked only by the role whose finding it answers, and only the fix; a verdict the re-check leaves standing carries forward, and the pull request records it.
3. **A wording fix.** The Coordinator itself fixes a documentation or wording finding of Tester or Reviewer, of any severity, whose fix touches only `*.md` files outside D10's excluded list, every hunk answering a named finding, while no Developer is at work in that worktree. No agent is started and it is no round. A verdict whose blocking findings were all of this kind counts, once they are fixed, as PASS or APPROVED for the fix. A documentation fix touching an excluded file is checked as before: a fresh Reviewer on the branch's whole change, and Tester reruns what it affects. A fix answering Codex is never a wording fix.
4. **A code fix.** For a Tester finding, Tester reruns that scenario and the criteria the fix touches, and the Reviewer verdict carries forward. For a Reviewer finding, a fresh Reviewer reads only the fix diff, `Base` the reviewed SHA, its earlier findings verbatim beside it; Tester runs only if the fix changes something a criterion checks. A fix answering both, or no finding — a CI fix, a flaky test, the Coordinator's own follow-up — is re-checked by both. A fix answering Codex is read by a fresh Reviewer on the fix diff, and Tester reruns what it affects in every case. CI runs for every SHA.
5. **Minors.** After APPROVED WITH MINORS no Reviewer runs again for them: a minor is fixed only when its fix carries forward or is a wording fix; any other goes into the pull request or a follow-up.
6. **Critical areas.** The areas marked `"critical": true` in `.claude/delivery-areas.json` are the one list: `migrations`, and the areas where a defect loses or leaks data, which `/flow-init` marks with the owner — where the project's blocking defects live (D15). When `delivery-queue.mjs areas <branch>` maps a branch into one, the full pair — Tester on every criterion, a fresh Reviewer on the whole change — runs once more on the SHA that is to merge, after main is integrated under the lock, unless their full verdicts are already for that SHA or carried to it by D10 or a wording fix. That pass is no round; a fix it calls for is.
7. **Merging main in.** An integration whose conflicts are none or only in the bookkeeping files is checked by the Coordinator by its diff, and CI runs: the verdicts carry forward and no Reviewer starts, but for a critical area. Any other conflict resolution goes to a fresh Reviewer on the whole change against the main SHA merged in, and Tester reruns what it affects.
8. **The Coordinator's edit right** (`CLAUDE.md`): besides integrating main and setting the version under the lock, it edits a task branch only for such a wording fix.
9. **Risk.** Outside the critical areas, nothing reads the whole change again after the first verdicts; inside them the full pair reads what merges, and CI runs for every SHA. Undo: revert.

## D20 — A Developer hands over to a fresh one at about 350k tokens of context; a command over about 4 minutes runs in the background; files are read in slices; grooming splits a large task into issues of its own

**Decision:**

1. **Why.** A Developer's cost per request grows with its context, and long runs cost several times more per request than short ones; automatic compaction did not fire in time. A sub-agent blocked past 5 minutes lets its prompt cache expire and rewrites it. File views re-read by every later request add up. Correction rounds and hours grow steeply with a task's size, so splitting pays mainly in time and rounds.
2. **Handover**, `developer.md`. The context is 15,000,000 less the tokens left that `total_tokens` shows. Below about 14,650,000 left, about 350k used, the Developer reaches a safe point, commits on the branch — or leaves the diff and says so where a commit would be wrong — and reports a handover note: done, left, files touched, commands run with their results, open risks, branch and head SHA, under the first line `Handover <sha> · checks: <the checks run> · left: <n>`. The Coordinator starts a fresh Developer with the original brief, the branch, the SHAs and the note, as a correction round starts a fresh one (D10); a handover is not a correction round.
3. **Long commands in the background**, `developer.md` and `tester.md`: a command expected over about 4 minutes — a full suite, an e2e run, an image build — runs with `run_in_background`, its output checked no more often than about every 4 minutes, and is stopped by its task id (D6).
4. **Slices first**, `developer.md`: Grep or a line range before a file; a whole file only when it is about 200 lines or less, or the change needs all of it.
5. **Split at grooming**, `/groom` step 2 and `/decompose` (D25): a task expected above about 1,000 lines of product code, or made of independent parts — frontend, backend and infrastructure, or a limit and its hostile shapes — becomes separate issues, each its own pull request. The scheduled grooming, which files no issue, proposes the split among its questions.
6. **Risk.** The rules are prose: an agent that misses the threshold or reads a file whole costs tokens, not correctness.

## D21 — Each job's model is chosen by a blind replay against known outcomes: the tester's grooming look runs as `tester-look` and the acceptance check of process-only pull requests as `tester-process`, both on Sonnet 5.5 at `xhigh`

**Decision:**

1. **The rule.** A job moves to a cheaper model or effort only when a blind replay measures it doing the job as well: over two runs per case, it finds at least as much of the ground truth as the job's current pin and invents no more blocking findings. Among the candidates that pass, the cheapest per completed job wins, and a tie goes to the current pin. A cheaper job gets a definition of its own under `.claude/agents/`, with a full model ID and an effort line, invoked without a `model` parameter (D8).
2. **The method.** Each case is past work whose outcome is known. The budget, and each job's ground truth, are posted before its runs. Every run is a headless `claude -p` session in a tree of its own — an export of the case's SHA, or a clone stripped of everything after it — given the role's body through `--agents`, the role's tools, no MCP server, and stand-ins for `gh` and `codex` that refuse; it reads no main checkout and no project memory, which its transcript is checked for. Answers are scored blind, under random labels, with the historical answers scored the same way as a reference.
3. **`tester-look`.** The tester's planning-only grooming look on Sonnet 5.5 at `xhigh` found as much as `tester` at `high` for about 29% less, so it moved, holding Read, Grep and Glob only — its "no Bash" is now a mechanism. Its body is the look's part of `tester.md`. The grooming still fingerprints the main checkout around the looks, since `tester` stands in when a session lacks `tester-look`.
4. **`tester-process`.** The acceptance check of a pull request whose every changed file is `*.md` or lies under `.claude/` — scripts and settings included, so the class holds code — and whose diff warrants no hostile-input pass, on Sonnet 5.5 at `xhigh`, found at least as much as the pin for about 20% less. It carries `tester.md`'s tools and body unchanged, which a test keeps equal; every other pull request, and one in the class whose diff warrants the hostile-input pass — it touches a parser, a formatter, a regular expression, redaction, or URL, header or request-line handling, the Bash guard for one — keeps `tester`. If the session lacks it (D4), `tester` verifies. The Bash guard refuses any `lsof` inside it as inside `tester` (D9).
5. **Kept.** The architect's grooming look on Opus 5.5 at `high`, the grooming session on Opus 5.5 at `medium`, and every other acceptance check: their cheaper candidates found less or invented a blocking finding.
6. **Limits.** Few cases, two runs each, one scorer; a pass resting on a tie of a half-item. A hostile-input pass, browser and deployed checks were not measured, hence the class's exception. On a process-only pull request the Reviewer and `tester-process` run on one model at one effort, so their misses may coincide: there the Reviewer is a second reading, not an independent model's.
7. **Rollback.** Revert the definitions and the routing; the look and every acceptance check go back to `tester`.

## D22 — The flow runs on GitHub: labels without scopes, exclusivity kept by whoever sets a state label, pull requests merged with a merge commit by the queue with `--match-head-commit`, tags pushed with git

**Decision:** The flow was built on GitLab and is ported to GitHub, where the kit lives.

1. **Labels.** GitHub has no scoped labels, so the names keep their scope as a prefix with one colon: `state:ready`, `state:grooming`, `state:needs-owner`, `state:deferred`; `type:bug`, `type:chore`, `type:idea`, `type:epic`; `prio:1` to `prio:3`; `delivery:attended`; `area:frontend`, `area:backend`, `area:docs`, `area:infra`. `/flow-init` creates them.
2. **Exclusivity is kept by whoever sets a label.** GitLab made a scope's labels mutually exclusive by itself; GitHub does not. So every command that sets a `state:` label removes the other `state:` labels in the same call — `gh issue edit <n> --repo <repo> --add-label state:ready --remove-label state:grooming,state:needs-owner,state:deferred` — and the same for `prio:`. A script that reads a state treats two `state:` labels on one issue as a fault to report, not as either state; the same for two `prio:` labels.
3. **Every `gh` command names `--repo <project.repo>`** (D11), and API reads write `--method GET` out.
4. **Pull requests.** A task's pull request is a draft, `gh pr create --repo <repo> --draft --base <main> --head <branch>`, marked ready with `gh pr ready` when it is to merge. It merges with a merge commit, so "the merge commit" stays the one SHA the main workflow runs for and the tag names; only through the queue's `merge` (D16), as `gh pr merge <n> --repo <repo> --merge --match-head-commit <full sha>`, so that GitHub refuses a head that moved since it was verified. No `--auto` (a merge under the lock happens now or fails), no `--admin`, no `--delete-branch`: the repository deletes head branches on merge, a setting `/flow-init` makes.
5. **Checks.** A pull request's checks are `gh pr checks`; a SHA's runs are `gh run list --commit <sha>`, read with `gh run view` and waited for with `gh run watch --exit-status`. The main workflow is `.github/workflows/<delivery.mainWorkflow>`, its jobs `validate`, `deploy` and `<delivery.smokeJob>`.
6. **Tags are pushed with git:** `git tag -a v<VERSION> <merge sha> -m "v<VERSION>"`, then `git push origin refs/tags/v<VERSION>`, verified with `git ls-remote --tags origin v<VERSION>`. Two commands the allow list can name exactly, and the tag is git's own annotated object rather than a release.
7. **Protection.** GitLab's protected branch becomes the repository ruleset `/flow-init` creates where the plan allows it (D24); where it does not, the Bash guard's push rule is the only mechanism (D26), and the documents say so.
8. **Consequence.** Every procedure, skill and script speaks `gh`; the issue number takes the place of GitLab's IID; GitHub Actions minutes take the place of CI minutes as a resource that can pause a task.

## D23 — `.claude/flow.json` is the one place a project configures the flow

**Decision:** `.claude/flow.json` holds everything that differs between projects using the flow: `project` (`name`, `repo` as `owner/name`, `mainBranch`, `site`, `ownerLanguage`), `commands` (`install`, `check`, `test`, `taskTest`, `taskDown`, `e2e`, `build`), `delivery` (`versioning`, `deploy`, `mainWorkflow`, `smokeJob`, `rollback`), `outsideReview` (`enabled`, `areas`), `design` (`figma`) and `schedule` (`cycle`, `grooming`, `morningFire`).

1. **Scripts read it through `.claude/scripts/flow-config.mjs`**: `loadFlow(root)` fills missing keys with their defaults, and a file that is missing, is not JSON or names no `project.repo` of the form `owner/name` is a `FlowConfigError` with one line. `FLOW_CONFIG` points a script at a fixture in the tests, and `node .claude/scripts/flow-config.mjs <dotted.key>` prints one value for shells and workflows. The procedures name a value as `commands.check` in `.claude/flow.json` and read it themselves.
2. **An empty string means the project has none of that thing**, and each step says what follows: no `taskTest`, and the suite is `commands.test`, so tasks must not share state the suite writes; no `rollback`, and recovery is a revert pull request; `deploy` false, and "deployment" is the main workflow's run for the merge commit passing, with no smoke and no site check; `versioning` false, and no `VERSION`, changelog entry or tag; `outsideReview.enabled` false, and the outside review is skipped with its reason; `design.figma` false, and the design reference is a saved image or a description in the issue.
3. **Why.** The flow's text and scripts stay the same in every project, so a fix to the flow can be carried from one project to another; what differs is data, in one reviewed file, changed by a pull request like any other change. No project's identity — a repository id, a host name, a command — is written into a script or a procedure.

## D24 — `/flow-init` sets a project up on the flow

**Decision:** `.claude/skills/flow-init/SKILL.md`, invoked as `/flow-init`, takes a new or existing repository to the point where `/decompose` and the scheduled runs can work. With the owner's answers it:

1. creates the repository from the kit's template, or configures the one it runs in;
2. fills `.claude/flow.json` (D23), the project placeholders of `CLAUDE.md`, and the stubs of `docs/PRODUCT.md`, `docs/ARCHITECTURE.md` (its `Stable parts` "none yet") and `docs/RESOURCES.md`;
3. creates the labels (D22);
4. sets the repository: merge commits only, head branches deleted on merge, no auto-merge;
5. lands the setup as the project's first delivery, through a pull request, its CI checks and the delivery queue's lock and merge, which proves `gh`, CI and the queue work;
6. creates the ruleset protecting the main branch where the plan allows it — a public repository, or a paid plan for a private one — and otherwise records that the Bash guard is the only protection (D26) and tells the owner the two ways to get real protection;
7. creates the two scheduled tasks (D17), or installs the launchd jobs on the owner's choice.

**The owner's authority date.** The owner's go-ahead to `/flow-init` is also the standing authority `CLAUDE.md` states for autonomous delivery of `state:ready` issues; `/flow-init` records that date in `CLAUDE.md`. A task-specific restriction still overrides it.

**Why.** The flow needs a dozen settings outside the repository — labels, repository settings, protection, schedulers — that are easy to get half right by hand. One skill makes them in order, through the same delivery the project will use, and says what it could not do.

## D25 — `/decompose` turns a big goal into an epic and small issues; it never sets `state:ready`

**Decision:** `.claude/skills/decompose/SKILL.md`, invoked as `/decompose`, takes a goal too big for one pull request, reads the project's documents and the tree at `origin/main`, asks the owner one round of questions, and files a `type:epic` issue — the goal, its observable end state, what is out of scope, and a `## Children` checklist — and its child issues: vertical slices, each one pull request (D20), each leaving the product working, opening with `## Problem` (D1) and carrying `Epic: #<epic>` and one `Depends on #<n>` line per prerequisite. In an empty project the first child is the scaffold, on which every other depends. It writes issues only, never the repository: no branch, worktree, commit or pull request.

1. **It never sets `state:ready` on its own.** The owner does, on an explicit word — the skill offers to make the first children ready and sets the label only then, removing any other `state:` label (D22) — or the scheduled grooming on its narrow class (D14); the children are groomed like any other issue.
2. **The order is carried by the issues.** The cycle's `pick` passes over an issue whose dependency is still open (D16), so the children deliver in the order their `Depends on` lines give, independent ones side by side.
3. **The epic is never groomed or delivered.** The delivery cycle ticks its boxes as children are delivered and closes it when the last one is.
4. **Why.** The flow delivers small issues well and large ones badly (D20); a goal given whole would be groomed into questions or delivered as one long pull request. Decomposing it once, with the owner, gives the grooming and the cycle work they can do.

## D26 — The Bash guard also refuses pushes to the main branch and force pushes

**Decision:** Besides D9's rules, `.claude/scripts/guard-bash.mjs` refuses, in every session, a `git push` whose refspec targets the main branch — `main`, `HEAD:main`, `refs/heads/main`, any of them after `+` — and any force push, `-f`, `--force` or `--force-with-lease`. A push of a task branch (`git push origin HEAD`, `git push --set-upstream origin HEAD`) and of a tag (`git push origin refs/tags/v<VERSION>`) passes.

1. **Why.** GitLab refused a push to the protected main branch on the server. GitHub Free offers no branch protection and no rulesets for a private repository, so there nothing on the server stops an agent pushing to main or rewriting history; the guard is then the only mechanism. Where `/flow-init` could create a ruleset (D24), the guard is a second layer that refuses before the network is touched.
2. **Consequence.** Main changes only by a merge through the queue (D16). A push with no refspec pushes what the current branch tracks; with commits on `main` refused (D9), an agent has nothing of its own on `main` to push. The limits of D9 item 6 hold here too: a push built through `sh -c`, a variable holding the refspec or a script file is out of the guard's reach and stays a rule in prose.
